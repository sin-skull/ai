# iPhone Safari で回答モデルが落ちる問題：候補の整理（2026-10-13）

この文書は、実機で起きたことと、コードとライブラリを読んで分かったことを分けて書く。**原因はまだ特定できていない。**「確認済み」と書いたもの以外は推測。

## 実機で起きたこと（ユーザーの報告）

端末は iPhone 17、Safari 27.0.1。UA は `iPhone OS 18_7`（固定値）。試験室で見えた端末の性質は次のとおり。

- WebGPU：あり。maxBufferSize と maxStorageBufferBindingSize はどちらも 1024MB。
- JSPI：あり。
- crossOriginIsolated：なし（GitHub Pages ではヘッダーを付けられない）。
- CPU の数：4。

## 候補

### A. 実行ライブラリ（Transformers.js 4.3.1 と onnxruntime-web）と Safari の組み合わせ

- **A1. WebGPU の命令の出し方。** WebKit の不具合報告 #311598 によると、iOS 26 では、1回の送信に計算の段階（compute pass）を数百入れると止まる。報告の中には、比較として「Transformers.js は Safari でメモリが増え続けて落ちた」という記述もある。症状 #4〜#7 と合う。**有力。**
- **A2. 読み込み時のメモリの山。** Transformers.js はモデルのファイルを Cache Storage から `arrayBuffer()` で丸ごと読む。続いて ORT のメモリ（wasm）または GPU のバッファへ写す。そのため、ファイルの大きさの2〜3倍が一時的に要る。#1、#3（約500MB）と合う。**有力。**
- **A3. 量子化の形式。** q4 の ONNX は `GatherBlockQuantized` を使うが、wasm 版の ORT はこれを実装していない（#2、確認済み）。q8 は動くが大きい。
- **A4. 長い入力の一括計算。** 日本語は細かく分かれるので、入力が長いと最初の計算（prefill）が大きくなる。#7 と合うように見える。ただし、300字に分けても落ちたので、これだけでは説明できない。

### B. アプリの作り

- **B1. 2つのモデルが同時に載る。** 意味検索（e5, 約120MB）と回答モデルを同時に持つ時間があった。v0.11.0 で、答えを作る間だけ外すようにした。ただ、バックグラウンドのベクトル作成、起動時の自動読み込み、連打は、まだ重なりうる（コードで確認）。→ v0.12.0 で、全てのモデル操作を1列に並べる。
- **B2. 落ちた処理を、次の起動でまた自動でする。** #8（確認済み）。v0.11.3 で直した。v0.12.0 で、全ての段階に広げる。
- **B3. 段階が分かれていない。** 「読み込み」の中に、ダウンロード、展開、最初の計算が混ざっていた。どこで落ちたか分からない。→ v0.12.0 で段階を分けて記録する。

### C. モデル

- **C1. LFM2 の構造。** LFM2 は畳み込みと注意を混ぜた構造で、ORT の WebGPU で、まだ枯れていない演算を使っている可能性がある。Qwen（Transformer のみ）と比べる必要がある。
- **C2. 大きさ。** 350M〜0.5B の4bit版は 220〜430MB。iPhone のタブで許されるメモリの量は公表されていないので、実測で決めるしかない。

### D. Safari（WebKit）全般

- **D1. タブのメモリの上限（jetsam）。** 値は公表されていない。超えると、例外ではなく強制終了になるので、ページの側では捕まえられない。
- **D2. 保存領域の片付け。** 入口ごとに別の保存領域になる（Safari のタブと、ホーム画面のアプリ）。
- **D3. WebGPU の上限の値は、動く保証にならない。** 1024MB と出ても、実際に確保して計算できるかは別。

## 方針（v0.12.0）

1. 段階を分けて記録する：ダウンロード → 初期化 → 最初の計算 → 資料の読み込み → 回答の生成。記録は、開き直したあとに見られる。記録には段階名、数値（字数、トークン数、秒）、方式だけを残し、質問の本文は残さない。外部にも送らない。
2. モデルは1つずつ載せる。全てのモデル操作を1列に並べ、次のモデルを読む前に前のモデルを外す。
3. 実行ライブラリを比較できるようにする。wllama（llama.cpp の Web 版）の CPU、分担、GPU の3つと、これまでの Transformers.js。wllama はモデルのファイルを OPFS から少しずつ読むので、A2 の山を避けられる見込み（ライブラリの作りとして確認、実機は未確認）。CPU なら A1 も避けられる。
4. 落ちた条件は、自動ではくり返さない。同じ条件で2回落ちたら、一段軽い方式へ自動で切り替える（GPU → 分担 → CPU）。
5. 試験室で段階を追って確かめる：短い答え → 検索との連携 → 長い資料 → 連続10問。速さと日本語の品質（期待する語が含まれる割合、資料との一致率、日本語の割合）も記録する。

## この環境（開発用の Chromium）で確かめたこと・確かめていないこと

**確かめたこと（自作の極小モデル、CPUだけ）：**
- 試験室の5つの試験：読み込み、短い答え3回、検索と連携5問、長い資料（約1700字を4つの塊に分けて読む）、連続10問。全部通った。Safari と同じ「互換版」（JSPI なし）に切り替えた状態でも通った。
- アプリ：有効化 → 10問連続 → 再読み込み（自動で読み込み直す）→ オフラインモードで答える。全部通った。
- 記録に質問の本文が入らないこと。
- 強制終了の状態を作って開いたとき：自動では読み込まない、資料の量を1段下げる、2回目は方式を1段軽くする、3回目はオフにする。いずれの場合も、保存した単語・文章は消えない。

**確かめていないこと：**
- iPhone の Safari での動作。
- 本物のモデル（LFM2 350M など）での動作。この環境からは Hugging Face のモデルを取得できない。
- GPU と分担。この環境の Chromium には、使える GPU が無い。
- 日本語の品質と速さ（極小モデルでは測れない）。
- 意味検索との入れ替え（e5 を取得できない）。


## 実機の結果 1（v0.12.0、2026-10-13）

試験室で、配管テスト用の極小モデル（0.5MB）を「CPUだけ」で動かした。

- ダウンロード（保存分の確認）：0.3秒で終わった。
- モデルの初期化：始まったまま、約9分半終わらず、ページを開き直したときに「途中で強制終了」と記録された。
- 使った実行用ファイル：速い版（Safari 27 は JSPI と 64bit メモリを持つので、wllama も私の判定も速い版を選んだ）。

**分かったこと：** 0.5MB のモデルを CPU だけで動かして止まったので、メモリ不足でも GPU でもない。実行用ファイル（速い版）と Safari の組み合わせで、初期化が進まない可能性が高い。wllama の説明でも、Safari の速い版は「動かない」とされている（互換版なら動くとされる）。

**v0.12.1 での対応：**
- iPhone・Safari では、自動で互換版を使う。試験室では、互換版と速い版を選べる。
- 初期化と最初の計算に時間の上限を設けた。上限を過ぎたら、止まったと見なして worker を止め、エラーとして記録する。
- 初期化の中の細かい進み具合（実行用ファイルの準備、llama.cpp の記録）を、「最後の処理」として残す。強制終了しても、どこまで進んだかが分かる。
