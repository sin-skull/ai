# ロードマップ

「頭脳は共通、記憶は各自」の自作AIを、単一HTML（PWA）として作る。フェーズ0〜8が v1.0、フェーズ9（ジャービス化）はその後の拡張。

**最終ゴール：自然な言葉で話せること。**（辞書・検索・回答・育ちは、そこへ向かう土台。）

**方針：すべてスマホの中で完結させる。** PC・自前サーバー・中継は要らない構成にする。ネットを使うのは、本人が許可した情報源への検索と、モデルなどの一度きりの取得だけ。取得したものは端末に残り、機内モードでも使える。取り込み・ベクトル作成・会話・整理も、すべて端末の上で行う。

## フェーズ1 記憶の核（2〜3週）

小さく3つに区切って進める。

- **1-A（完了）**: IndexedDB の土台、単語の正規化、単語辞書、チャット形式の画面（Claudeのアプリを参考にした入力欄と、左の記憶パネル）
- **1-B**: 文章の保存・一覧・削除と、n-gram のキーワード検索
- **1-C**: 👍/👎の評価、保存前の確認画面、手動入力フォーム、テストの拡充

目的は、モデルも検索も使わずに「保存する・探す・評価する・消す」を一通り動かすこと。

- [x] IndexedDB のラッパー（open、トランザクション、版管理と移行）
- [x] 単語の正規化（前後空白、全角半角、大文字小文字、カタカナ・ひらがなの扱い）
- [x] 単語辞書：同じ語は1件に統合。定義が違うときは「上書き／追記／無視」を選べる
- [x] 文章ストア：追加、一覧、全文表示、1件削除、複数削除（API）。削除しても単語辞書は残す（`deleteTerms` で一緒に消す選択肢）。※画面の複数選択はまだ（1件ずつ削除）
- [x] 保存前の確認画面（長文：文章として保存／保存しない。Wikipedia：単語と文章で覚える／単語だけ覚える／次の候補／やめる）
- [x] 文字2-gramの転置インデックスでキーワード検索（保存・削除と同じトランザクションで更新。語はAND、本文照合で誤検出を除く）
- [x] 評価：👍/👎ボタン。押すたびに feedback ログを残し、対象の評価値を更新（同じ向きの再押しは取り消し、逆向きは付け替え）
- [x] 入力はチャット形式（下の入力欄）。「単語 = 意味」で覚え、「AIとは？」で答える（1-Aで実装済み）。長文（80字以上／2文以上／改行つき40字以上）を送ると、確認のうえ文章として保存する（1-Bで実装済み）
- [x] ブラウザで開ける簡易テストページ（保存・検索・削除・統合の回帰テスト）

**ゲート**: 同じ語を2回保存しても1件／保存した文章が検索で見つかり、削除すると結果から消える／リロードしてもデータが残る／👍/👎が評価値に反映される。

**リスク**: 日本語の正規化の細かさ。インデックスと本体の不整合（削除とインデックス更新は必ず同じトランザクションで行う）。

## フェーズ2 オフライン化（1〜2週）

目的は、電波の無い場所でもアプリを開けて、記憶を失わないこと。「オフラインモード」は、端末の接続状態とは別に、自分で切り替えるスイッチにする。

- [x] `manifest.webmanifest` とアイコン（180/192/512px）
- [x] Service Worker（`sw.js`）：アプリ本体をキャッシュ。画面は「繋がれば最新・無理ならキャッシュ」、JSは版番号つきでキャッシュ優先。古い版のキャッシュは起動時に削除。`sw.js` の VERSION と index.html の `?v=` は一致させる（テストで検出）
- [x] モード切替（オンライン／オフライン）を settings に保存。外部通信は `AI.net.fetch` だけを通し、オフラインモード中は通信前に止める（外部通信ゼロをテストで確認）
- [x] 保存領域の永続化をリクエスト（`navigator.storage.persist()`）し、結果と使用量（`storage.estimate()`）を表示
- [x] JSON の書き出し／読み込み。読み込み時は「統合／置き換え」を選べる（iPhone は共有シート経由で保存）
- [x] モードが一目で分かる表示（ヘッダーの丸いボタン。押すと切り替え）

**ゲート**: 機内モードでアプリが起動し、保存済みの知識を検索できる／オフラインモード中に外部通信が1件も発生しない（開発者ツールで確認）／書き出し→全削除→読み込みで完全に復元できる。

**iPhone での前提**: 1回目はネット経由（https）で開く必要がある。そのあと Service Worker がアプリ本体を端末に保存するので、機内モードでも開ける。Safari のタブのままだと、一定期間使わないと保存データが消されることがあるため、「ホーム画面に追加」して使う（追加したアプリはこの扱いから外れる）。ファイル（file://）として端末に入れる方法は、保存データが安定しないので採らない。

**リスク**: ブラウザが容量不足や長期間の未使用で保存データを消すこと。iPhone では特に注意が必要で、ホーム画面への追加や永続化の要求でも保証はされない。定期的な書き出しを促す表示（最後に書き出してからの日数）を入れる。

## フェーズ3 検索の入口（2週）

目的は、成長の源である「検索→確認→保存」の流れを作ること。最初は中継なしで直接読める検索元だけで始め、必要になってから中継を足す。

**3-A 直接読める検索元（中継なし）**

- [x] Wikipedia API で検索→候補一覧→本文取得→保存前確認→蓄積
- [x] 出典URL・取得日・ライセンス表記（CC BY-SA 4.0）を文章・単語と一緒に保存し、一覧と答えにも表示
- [x] 外部に送る前に、送信する検索語を画面に表示して確認できるようにする（個別は「Wikipediaで調べる」の注記、まとめては送る語の一覧＋確認）

**3-B 未回答キュー**

- [x] オフラインや知識不足で答えられなかった質問を queue に残す（同じ質問は重ねず回数を数える。覚えると自動で外れる）
- [x] オンラインに戻ったとき「未回答がN件あります」と表示し、まとめて調査を開始できる（「未回答」タブにも件数と一覧）
- [x] 調査結果は自動保存せず、候補として並べて、どれを残すかを自分で選ぶ（覚える／次の候補／あとで／いらない）

**3-C 中継（Cloudflare Workers、必要になったときだけ）**

- [ ] 任意URLの本文取得と、検索APIのキー管理だけを担当する小さな中継
- [ ] データは保存せず、ログも残さない。自分専用のトークン認証を入れ、許可する宛先を絞る
- [ ] 無料枠の上限をアプリに表示し、超えそうなときは警告する

**ゲート**: オンラインで質問するとWikipediaから候補が出て、選んだものだけが保存される／オフラインで答えられなかった質問がキューに溜まり、オンライン復帰後に処理できる。

**リスク**: 検索APIの無料枠・条件の変更、他サイトの利用規約、中継の悪用。無料枠の数字は設定値として外に出す（コードに埋め込まない）。

## フェーズ4 意味検索（2〜3週）

目的は、言い換えた質問でも関連する知識を見つけられるようにすること。モデルは全員同じものを配り、ベクトルは各自の端末で作って端末内だけに保存する。

- [x] Transformers.js（4.3.1。リポジトリには置かず、有効化したときに jsDelivr から取得。SHA-256 を照合して端末に保存）で多言語e5-smallをブラウザ内で動かす。有効化の確認画面（容量・通信先を表示）、ダウンロード進捗、動作確認まで実装。**実モデルで動作を確認済み**（2026-10-12、利用者の端末。準備27.9秒・文章30件の処理1.3秒・検索22ms）。**機内モードでの意味検索も利用者の端末で確認済み**（2026-10-12、言い換え3問で正解が1位、無関係な2問は「知らない」）
- [x] 文章を保存するときにベクトルを作り、vectors ストアに保存（段落・文の切れ目で最大300字のチャンクに分割。1つ目にはタイトルを付ける）
- [x] 検索はコサイン類似度の総当たり（文章ごとに一番近いチャンクの点を使う）。近似検索は未着手
- [x] キーワード検索と意味検索を組み合わせる（順位の合算 RRF）。意味が使えないときはキーワードだけで答える。「近さ」が閾値（0.84。評価セットで決定）未満の意味検索の結果は捨てる
- [x] ベクトルにモデル名と版を持たせ、異なる版は作り直す（進捗表示・中断・再開に対応。書き出しには含めず、読み込み後に自動で作り直す）
- [ ] モデルパック選択画面（軽量／標準／大容量）。今は「標準」1種類。容量と端末の空き容量は確認画面に表示済み
- [x] 自作の評価セット（文章30件・質問36件・関係ない質問6件）と実行ページ `tests/eval.html`。結果は docs/EVAL.md に記録する（言い換えの質問：キーワード 41% → 意味検索 97%）

**途中でわかったこと**: キーワード検索は、日本語の質問（空白なし）だと文全体が本文に入っていないと何も出なかった。2文字の並びの一致割合で拾う「ゆるい検索」を足した（内容を表さないひらがなだけの組は数えない）。

**ゲート**: 言い換えた質問で関連する保存文章が上位に出る（評価セットで数値を記録）／機内モードでも意味検索が動く／文章を削除するとベクトルも同時に消える。

**リスク**: モデルの容量、iPhone でのメモリ不足、WebGPU と WASM の端末差。端末で動かないときはキーワード検索だけで動くようにしておく。

## フェーズ5 回答生成（3〜4週）

目的は、検索で見つけた保存文章を読ませて、自然な文章で答えさせること。

- [x] 検索→上位文章（最大3件・計1400字まで）をプロンプトに入れて回答させる流れ（RAG）。質問に近い文を優先して詰める
- [x] ブラウザ内LLM：Transformers.js で Qwen2.5-0.5B-Instruct（q8・約520MB・Apache-2.0）。有効にするときだけダウンロード。**実機での動作は未確認**（この環境からは取得できないため、疑似ジェネレータで仕組みを確認）。1.5B 以上は容量とメモリの都合で載せていない
- [x] 端末が非対応・読み込み失敗・オフのときは、「保存文章の抜粋を並べる」表示にフォールバック
- [x] 回答には根拠（番号つきの保存文章）を表示。根拠を押すと全文と👍/👎が出る。資料に無い言葉が多い答えには警告（根拠度が0.5未満）
- [x] 資料に答えが無いときは「わかりません」と答えさせ、未回答キューに入れる（プロンプトの縛り＋検索の閾値）。資料の中の命令には従わせない指示つき
- [ ] 任意機能として、オンライン時だけ外部LLMを併用（送信内容を確認してから送る）。未着手
- [x] 口調：ていねい／くだけた／簡潔／自分で書く（80字まで）。メニューで変更、設定は端末に保存
- [x] **ダウンロードの管理**：保存済みのモデルは取り直さない（確認画面で「ダウンロードしません」と表示。オフラインモードでも有効化できる）／有効化の二重実行を防ぐ／実行用ファイルは意味検索と回答で共有／メニューの「端末に保存したもの」から1つずつ2回押しで消せる（使用中のものを消すとその機能はオフになる）／オフにするときは「残す」「端末から消す」を選べる
- [ ] 回答の質を評価セットで記録：評価ツール（tests/eval.html の「回答も評価」）は作成済み。**実モデルでの測定は未実施**

**ゲート**: 機内モードで、保存済みの知識に基づく回答が根拠付きで出る／保存文章に無い質問で「知らない」と答えてキューに入る／非対応端末でもフォールバック表示で完結する。

**リスク**: 小型モデルの誤答、端末の発熱と電池消費、モデルのダウンロード容量。モデルのライセンスは配布前に確認する。

## フェーズ6 成長の仕組み（2週）

目的は、「よく使われて感謝された知識が残り、間違った知識が消える」循環を作ること。モデル自体は賢くならないので、成長するのは蓄積された知識の質だけ。

| 軸 | 範囲 | 更新のきっかけ |
| --- | --- | --- |
| 評価（ポジ/ネガ） | -1〜+1 | 👍/👎を主に。「ありがとう」「違う」などの言葉は補助の信号 |
| 重要度 | 0〜1 | ピン留めなど、自分で明示したとき |
| 確信度 | 0〜1 | 出典の数、複数の出典で内容が一致しているか |
| 使用回数 | 0以上の整数 | 回答の根拠に使われたとき +1 |
| 最終使用日 | 日付 | 根拠に使われたとき |
| 取得日（鮮度） | 日付 | 保存時。再取得したときに更新 |

- [x] 検索順位に評価・重要度（ピン留め）・新しさを重みとして反映（検索で「関係あり」と判定された結果の並べ替えにだけ使う）。重みはメニューの「設定と保存 → 並び順の重み」で0〜50%に調整、0%で無効。初期値は評価10%・ピン10%・新しさ5%
- [x] 言葉からの評価：「ありがとう」「違う」など短い決まった言葉だけを辞書ルールで読み取る。答えの直後の1回だけ、答えの主な根拠だけを評価。**明示の👍/👎が付いていれば上書きしない**。「評価を変更しました」と表示し、取り消せる。叱責・悪口（「使えない」など）は評価にしない
- [x] 使用回数と最終使用日：回答の根拠に使われたとき・文章や単語を開いたときに記録
- [x] 整理候補（「整理」タブ）：低評価 > 未使用（保存から30日以上）> 古い（180日以上）の順。ピン留めしたものは出さない。削除は「消す」を2回押して確認。「📌 残す」で候補から外せる
- [x] 古い知識の再取得：Wikipedia由来の古い文章に「Wikipediaで再取得」ボタン（押したときだけ記事名を送る・オフラインでは無効）。評価・ピン・使用回数は引き継ぐ
- [x] 成長の可視化：蓄積数の週ごとの推移（手描き風の棒グラフ）、よく使われた知識、👍/👎/📌/未回答の数
- [ ] 実機での確認（順位の変わり方・言葉の評価・整理）
- [x] Wikipedia検索の精度：文の質問は内容語だけ取り出して送る（「植物はどうやって太陽の光から栄養を作るの」→「植物 太陽 栄養」。実機で「葉」の記事が出た不具合の修正）／記事名がぴったり一致するものを先頭に／候補は最大5件で題名から直接選べる／「別の言葉で調べる」

**ゲート**: 👍/👎を付けた結果が次回以降の検索順位に反映される／整理候補から選んで削除できる／感情分析の誤判定があとから取り消せる。

**リスク**: 口調の強さと内容の正しさを混同すること。叱責の言葉をそのまま低評価にしない。明示の操作を優先する。

## フェーズ7 知識を広げる（3〜4週）

目的は、保存した文章だけに頼らず、外の情報と大量のデータを、**スマホの中で**意味で探せる形で取り込めるようにすること。

実機で出た課題：「調べる」（Wikipedia検索）は言葉の一致で探すため、言い換えの質問に弱い（質問の文をそのまま送ると、的外れな記事が出た）。文の質問は内容語だけ送るよう直したが、根本は並べ替えが要る。

### 7-A 「調べる」を意味で選び直す
- [ ] Wikipedia の候補を10件ほど取り、手元の意味検索モデルで質問に近い順に並べ替える。近さが閾値未満なら「近い記事は見つかりませんでした」と言う（意味検索がオフならキーワード順のまま）
- [ ] 回答モデルがオンなら、質問を検索向けの言葉に言い換えさせる（失敗したら内容語の抜き出しに戻す）
- [ ] 評価：Wikipedia の応答を固定データとして保存し、通信なしで並べ替えの正解率を測る（`tests/eval/`）
- [ ] 送るのは検索語だけであることを、これまでどおり画面に出す

### 7-B 取り込みと知識パック（端末内で完結）
- [ ] ファイルの取り込み：`.txt` `.md` `.json` `.csv`（共有シート／ファイル選択から）。見出し・段落で自動分割（1件 ≤ 800字）、同じ本文は取り込まない（重複排除）
- [ ] 取り込み単位を「パック」として管理：名前・件数・容量・ライセンス・出典メモ。一覧、無効化（検索から外す）、パックごとの削除ができる（保存したものを消せる原則を、データにも広げる）。ライセンス欄は必須
- [ ] ベクトルの作成は端末内で、バックグラウンド・中断と再開に対応。進捗表示と、電池・発熱の注意（充電中・Wi-Fi推奨）。画面を閉じても続きから再開できる
- [ ] 規模の実測：1万件の作成時間と、検索が遅くなる件数を測り、上限の目安を決める。必要なら、ベクトルの量子化（int8）や検索対象の絞り込みを入れる。現時点の見積もりは「1万件で約7分、5万〜10万件が上限」（未実測）
- [ ] パックも書き出し・読み込みの対象にする（ベクトルは含めず、読み込み後に作り直す）
- [ ] Wikipedia 全体は端末に大きすぎるため、人気記事の冒頭など、必要な分野だけのパックを自分で作れるようにする（記事名の一覧から、端末内で取得して作る）

### 7-C 情報源の追加
- [ ] 情報源の登録表（名前・検索窓口・ブラウザから呼べるか（CORS）・ライセンス・使う条件）を作り、情報源ごとにオン/オフできる。送る前に、どの情報源に何を送るかを確認画面に出す
- [ ] 候補：英語版 Wikipedia、ウィクショナリー、Wikidata、青空文庫、e-Gov 法令検索、国立国会図書館の検索API。**ブラウザから直接呼べないものは採用しない**（中継を使わない原則）。どれもこの環境からは繋がらないため、実機で確かめる
- [ ] 任意：自分のAPIキーでウェブ検索（キーは端末内にだけ保存。質問が外部に出る旨を毎回確認）
- [ ] 取得した内容は、出典とライセンスを一緒に保存する（パックまたは文章として）

**ゲート**: 言い換えた質問で、Wikipedia の正解記事が上位に出る（数値を記録）／テキストファイルを1000件以上取り込み、意味検索できる／機内モードで、取り込み済みデータの検索が動く／パックごとに消せて、消すとベクトルも消える。

**リスク**: iPhone のメモリと保存容量、ベクトル作成中のアプリ中断・発熱、取り込むデータの著作権（自分で用意したものか、ライセンスを確認したものだけを入れる）、CORS 非対応の情報源。

## フェーズ8 会話（3〜4週）

目的は、最終ゴールである「自然な言葉で話せること」。いまは「保存文章を根拠に答える」までで、前の発言を踏まえた会話や雑談はできない。これをスマホの中で作る。

- [ ] 会話履歴：直近の数往復を保持し、プロンプトに入れる（長さの上限で古いものから切る）。「それ」「さっきの」などの指示語は、履歴から補って検索する（質問の書き直し）
- [ ] 意図の振り分け：雑談／質問／覚える／操作を、ルールで判定し、迷ったときだけモデルに聞く
- [ ] 雑談：根拠が無いときも、「保存した文章に根拠のない会話です」と印を付けた上で返す。事実は断言しない。根拠があるときは、これまでどおり根拠付きで答える
- [ ] 口調・キャラの一貫性（システムプロンプト）。利用者が話した好みを、本人の確認を取って覚える
- [ ] モデルの選択制：標準（0.5B）に加え、大きいモデル（1.5B級。端末のメモリと WebGPU の有無で可否を判定し、動かない端末では出さない）。端末で速度・メモリ・品質を測って記録する
- [ ] 任意：オンライン時だけ外部の大きなモデルを使う（自分のAPIキー、端末内にだけ保存、送る内容を毎回確認）。オフラインでは使わない
- [ ] 評価：会話の評価セット（指示語・雑談・知らないこと・作り話をしないこと）を作り、実機で測る

**ゲート**: 機内モードで、前の発言を踏まえた3往復以上の会話が成立する／根拠のある答えと雑談が見分けられる／知らないことは「知らない」と言える。

**リスク**: 小型モデルの会話の質（0.5B では限界がある）、大きいモデルが iPhone で動かないこと、雑談での作り話。質を上げる最後の手段は外部モデルの任意併用。

## フェーズ9 ジャービス化（3〜4週、v1.0の後）

目的は、質問に答えるだけでなく、自分のアプリや操作を声や文章で動かせるようにすること。

- [ ] 意図の振り分け：「開いて」「流して」「調べて」「覚えて」などをルールで判定し、判定できないときだけモデルに聞く
- [ ] 操作対象の登録表（名前、呼び方、開くURL）を設定画面で編集できるようにする（本棚アプリなどの自作アプリを登録）
- [ ] 「開いて」「流して」は確認不要の軽い操作、削除や外部送信を伴う操作は必ず確認を挟む
- [ ] 音声入力：Web Speech API（端末差あり）から始め、オフライン対応が必要なときは Whisper 系のブラウザ内モデルを検討
- [ ] 音声出力：Web Speech Synthesis で読み上げる
- [ ] 「覚えて」で単語辞書や文章へ保存、「忘れて」で削除できるようにする
- [ ] 常時待ち受け（起動語）は電池を消費するため、最初は押して話す方式だけにする

**ゲート**: 「本棚アプリを開いて」と言う（または打つ）と、登録したアプリが開く／「〇〇を調べて」でフェーズ3の検索フローが始まる／「〇〇を忘れて」で対応する保存項目が削除候補として出る。

**リスク**: ブラウザのマイク権限、iPhone での音声認識の制限、誤認識で誤った操作をしてしまうこと。破壊的な操作は確認必須として防ぐ。

## 横断事項

### プライバシーの約束（全フェーズ共通）

- 外部に出るのは、確認した検索語（と、許可した情報源への問い合わせ）だけ。保存文章や辞書は送らない。
- 現在は中継を使わず、ブラウザから直接つなぐ。中継を入れる場合も、ログを残さず、データを保存しない。
- 各自のデータでモデルを追加学習しない。共有する部品は読み取り専用。
- クラウド同期は入れない。バックアップはユーザーが手で書き出して保管する。

### ライセンスと規約（配布前に必ず確認）

- Wikipedia の本文は CC BY-SA。出典表示と同じライセンスの継承が必要。
- 埋め込みモデルと LLM のライセンス（商用・再配布の可否）をモデルごとに確認する。
- 他サイトの全文保存は個人利用の範囲に留め、サイトの規約を確認する。
- 検索APIの無料枠の数字は変わりやすい。実装前に公式で確認する。

### 主なリスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| ブラウザが保存データを消す | 記憶を失う | 永続化のリクエスト、定期的な書き出しの促し |
| 小型モデルが作り話をする | 誤った回答 | 根拠の必須表示、「知らない」と答える仕組み、評価セット |
| 端末が WebGPU に非対応 | 回答生成が動かない | 検索結果の提示にフォールバック |
| モデルとパックが大きすぎる | 初回が重い、容量不足 | 軽量/標準/大容量の選択制、容量を事前表示 |
| 中継の悪用や上限超過 | 不正利用、課金 | トークン認証、宛先の許可リスト、上限超過で停止 |
| インデックスと本体の不整合 | 検索結果が壊れる | 同じトランザクションで更新、インデックスの再構築機能 |
| 大量データで端末が重い・落ちる | 取り込み中の中断、発熱 | 中断と再開、バックグラウンド処理、件数の上限の実測、パック単位の無効化 |
| 情報源がブラウザから呼べない（CORS） | 調べられない | 呼べる情報源だけを採用する。中継は使わない |

## 補遺：端末の保存領域について（v0.10.2）
- iOSでは、Safariのタブと、「ホームに追加」したアプリは、それぞれ別の保存領域を持つ。記憶もモデルも共有できない（アプリ側からは回避できない）。ホームに追加し直すたびに、空の領域ができる。
- 対策：入口を1つに決める。移すときは「書き出す／読み込む」を使う。「記憶を全て消す」「初期状態に戻す」を用意した。
- 回答モデル：軽量（LFM2 350M・約510MB・8bit。4bit版は実機で動かなかったため）を追加し、既定にした。読み込み中に落ちたら、次の起動で自動オフにして、どの段階で落ちたかを表示する。モデルが使えない端末向けに、文章から文を抜き出す機能（モデル不要）を付けた。実機での動作は未確認。

## 補遺：v0.10.5
- 1回の送信に複数の質問を入れられる（改行、または「？」の後ろで区切る。全部が質問のときだけ。最大5つ）。
- 質問欄の下に「知らないことは自動で調べる」スイッチ（初期はオフ）。オンだと、保存した記憶に無い質問を確認なしでWikipediaに送り、一番近い記事を文章として保存して、その場で答える。違う記事なら取り消して選び直せる。オフラインモード中は送らない。
